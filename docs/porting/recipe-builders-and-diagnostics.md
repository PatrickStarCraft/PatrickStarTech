# Recipe builders and reliable compiler diagnostics

AI-assisted implementation and verification by OpenAI Codex, 2026-09-21. Human review is required before contribution under AI_POLICY.md.

## Actual recipe migration

Shaped, shapeless, cooking and shaped-energy builders now serialize ingredients through Ingredient.CODEC and outputs through ItemStackTemplate.CODEC. Component-bearing input stacks use NeoForge's exhaustive DataComponentIngredient; plain stacks remain item-only matches. Empty stack inputs/results are rejected. Cooking builders use the serializers owned by the modern recipe classes and serialize their configured category.

Tag ingredients use named holders for serialization without resolving tag contents. Runtime-pack construction happens before those tags necessarily exist. These generation-only holders must not be used for runtime matching or item enumeration; loading the generated recipe resolves its tag against the loader's lookup context.

Each builder accepts an explicit registry provider via registries(...). VanillaRecipeHelper supplies GTRegistries.builtinRegistry(), preserving access to the current registry context for component codecs. Standalone builders default to the built-in registry provider; callers using components bound to dynamic registries must supply the appropriate provider. Builder copies retain the provider.

Outputs preserve counts and component patches. The old output(stack, count, CompoundTag) overload is now output(stack, count, DataComponentPatch); addons must migrate callers. No in-repository calls to the old three-argument overload were found. Vanilla-owned fields must use their own components, not be placed indiscriminately into CUSTOM_DATA.

For outputs and direct DataComponentIngredient inputs, minecraft:custom_data is emitted using CustomData's supported SNBT alternative. Ordinary JSON number conversion can narrow long/int/byte tag types; this would break strict matching and GT's LongTag-only MaxCharge override. Tests require exact custom-data types after decoding. Arbitrary nested third-party ingredient codecs remain outside this guarantee.

ShapedEnergyTransferRecipe now reads the real item capability and writes charge/capacity through ElectricItemData. This preserves other output components and does not mutate the input stack. Its existing first-matching-input behavior is unchanged. The previously unused overrideCharge/transferMaxCharge policy flags and recipe-book integration still need a separate behavioral review.

## Why the diagnostic total changed sharply

The original diagnostic compile stopped annotation processing when early enter/type errors occurred (including invalid inheritance and generic declarations). Consequently, javac also reported thousands of methods normally generated by Lombok as missing. This was not evidence that those methods needed handwritten replacements.

The installed Java 25 JavaCompiler source confirms that the default shouldStopPolicyIfError is INIT and processAnnotations returns early when shouldStop(PROCESS) is true. A diagnostic-only comparison with `-XDshould-stop.ifError=FLOW` allowed normal Lombok generation to proceed through attribution/flow while still reporting errors and returning failure. For example, the 77 missing isHighTier() and 35 missing pos() diagnostics disappeared without adding methods manually.

The existing opt-in `-PportDiagnostics` mode now supplies that flag. Ordinary build settings, dependency versions, Java versions and Lombok versions are unchanged. It is an internal javac option tied to the installed Java 25 diagnostic workflow, not a workaround that makes the release build succeed; reassess it on toolchain upgrades.

Counts must be distinguished:

- Before this builder slice, old diagnostic behavior: **8,887 errors**.
- After actual builder/API changes, old diagnostic behavior: **8,841 errors** (46 fewer).
- With proper annotation processing enabled for diagnostics: **5,442 errors**.

The last drop is primarily removal of misleading cascades, **not thousands of completed API migrations**. Use 5,442 as the new diagnostic baseline and do not compare it to old-mode counts as a measure of work completed. All these full compiles fail; no playable build exists.
